# Behavior checks

Use when a consequential instruction finding depends on model defaults, actual
invocation, permission handling, or a disputed stopping point. Prefer existing
task evidence and one bounded ordinary real-use check over a new evaluation
campaign. An unavailable check leaves the claim unverified.

State the behavior at issue, actual host/model and relevant settings, the source
revision, and an observable result that would support or contradict the finding.
Use a representative request and only the raw artifacts needed to perform it.
For an independent check, withhold the suspected defect and intended answer so
the checker exercises the instructions rather than repeats the conclusion.

Choose the case that distinguishes the claim. Invocation may need an intended
request and a nearby non-trigger; a completion change may need a fresh request
and an approved continuation. Use relevant cases, not a universal case count.
Inspect the actual response/actions, loaded instruction paths, and artifacts.
Metadata parsing or a role's completion message alone is not behavioral proof.

Keep checks within authorized resources and side effects. A read-only interaction
check can observe questions or proposed actions; it cannot establish successful
deployment, cleanup, installation, or promotion. Obtain separate authority for
operations that need it. Preserve unrelated state and any required human input.

Report the observation, counterevidence, and practical limits. Correct a demonstrated
in-scope defect at its owner and repeat only affected checks. A single successful
interaction supports that case, not universal reliability across models or hosts.
If ordinary evidence cannot resolve a material choice, return the precise
uncertainty to the user or existing evaluation owner; do not invent repeated
trials, a scoring system, or a permanent harness.
