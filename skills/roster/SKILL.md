# Roster

The coordinator (ORC) dispatches every delegated task from this roster. The
source of truth is [`roster/roles.toml`](../../roster/roles.toml) in the Orca Pod
repository; change models there and rerun `roster/generate.py`, never here.
Standing instructions for each role are in [roles.md](roles.md).

## Layers

- **pane:** ORC is the agent in the user's Orca pane. It owns dialogue,
  approvals, tracker writes, Git integration and final acceptance.
- **orca:** always an Orca sibling worker started with `worker-start`.
- **native:** a native subagent (`~/.claude/agents/<id>.md` or
  `~/.codex/agents/<id>.toml`) when the role's provider matches the
  coordinator's; otherwise an Orca worker. A role on the other provider is
  always an Orca worker.
  - Claude ORC: PLN and EXP-lite are native. Send a trivial few-file lookup to
    EXP-lite (`exp-lite`), never Claude Code's built-in Explore subagent, which
    inherits the coordinator's model with no effort pin. Anything that loops
    goes to EXP.
  - Codex ORC: EXP and MON are native.
- Native subagents are for short, read-only, single-provider help. Use an Orca
  worker for anything that edits, runs long, needs supervision or crosses
  providers. SEC is never native.

## Routing rules

1. **Only ORC selects models**, from the roster. Workers never reroute.
2. **Cross-provider review and proof.** REV and the independent bug proof
   (TST-proof, SEC-PROOF) run on the other provider from the implementer; every
   map-panel and spec-panel persona runs on the provider opposite the record's
   drafter. When WRK runs on Codex, REV flips to Claude Opus 5.5 xhigh and
   TST-proof to Claude Opus 5.5 medium. TST and BRW stay on Codex.
3. **Read the receipt; never trust self-report.** On every `worker-start`
   receipt, `launch.effective` must equal `launch.requested`. Report a mismatch or
   a failed launch to the operator. Never substitute a model or provider; there
   is no fallback. Never use a worker's own statement of its model or effort.
   Confirm with the provider records (below) whenever the model matters to the
   result and for every SEC launch.
4. **Effort escalation is explicit.** ORC may raise one effort level for a
   specific assignment, records why in the brief and the report, and uses the
   listed alternates only for their stated condition. Roles never self-escalate.
5. **Security triggers route to SEC** (security path below), including a
   safeguard refusal. Report every re-route.
6. **Every brief includes:**
   - the exact checkout and revision, and its dirty state
   - owned files and behavior
   - acceptance criteria and the evidence to return
   - authority: read-only, write within owned files, or a named Git action
   - the role's standing instructions, verbatim from [roles.md](roles.md)
   - the assigned model and effort, as information only
   - "No nested delegation unless authorized."
7. **Fan-out comes only from ORC.** Orca enforces nesting depth 1
   (`nested_worker_depth_exceeded`); keep it. Raising Settings → Orchestration →
   "Nested worker depth" is an explicit operator decision.
8. **Every managed agent is a `worker-start` dispatch.** Never use bare
   `orca agent launch` for work you manage: its sessions cannot be read or closed
   from the CLI.
9. **PLN drafts maps and specifications.** For a substantive map,
   implementation specification or material revision, delegate drafting to PLN
   with the operator's actual answers and the relevant repository evidence, and
   reuse that PLN for later revisions. ORC keeps the live dialogue, reconciles
   PLN's proposed text and publishes through the owning workflow. It routes the
   map pass through `wayfinder` and the spec panel through `to-spec`, and asks
   the human only for map decisions, the Chart-the-map confirmation and
   escalated panel findings. ORC may draft a compact, fully settled record itself and
   makes administrative updates without PLN.

Launch failures are reported, never rerouted. Delegation never expands
authority: workers do not commit, push, merge or publish unless that action is
assigned.

## Brief

Write the brief to a file outside the checkout and pass it with `--spec`:

```text
Role: <emoji> <TAG>. Assigned model: <model> at <effort> (information only; do not infer it).
Target: <repository>, worktree <selector>, revision <sha>, dirty state <clean | details>.
Change: <the concrete result>.
Ownership: <files and behavior this worker owns>.
Authority: <read-only | write within owned files | named Git action>.
Constraints: <invariants, do-not-touch boundaries>.
Acceptance: <checks, outputs or evidence that prove completion>.
Escalation: <none | raised from X to Y because ...>.
No nested delegation unless authorized.

Standing instructions:
<verbatim from roles.md>
```

## Commands

Bind one Run per coordinator session, then start the whole independent wave
before waiting:

```bash
orca orchestration run-create --objective "<objective>" --json
```

A coordinator consumes exactly one Run at a time. `run-create`, or binding any
other Run, rebinds the caller, and mutations on its other Runs then fail with
`consumer_fenced`. To switch back, rebind the original Run:

```bash
orca orchestration run-use --id <run_id> --json
```

`worker-start` exits 0 only when the worker is ready. On a non-zero exit, do not
relaunch: read `failedStage` and `residualResources` from the receipt and follow
Orca's `orchestration` skill recovery reference.

**Read-only role in the coordinator's checkout** (REV of ORC's own tree, TST,
BRW, EXP, MON, PLN, DSP):

```bash
orca orchestration worker-start --agent codex --model gpt-6.1-sol --effort xhigh \
  --worktree current --task-title "🔍 REV <purpose>" --spec "$(cat <brief-file>)" --json
```

**Editor in its own child worktree** (WRK, TST-proof, OPS when it edits files):

```bash
orca orchestration worker-start --agent claude --model claude-opus-5-5 --effort high \
  --worktree new-child --base-branch <branch> --name <short-name> \
  --task-title "🛠️ WRK <purpose>" --spec "$(cat <brief-file>)" --json
```

`--base-branch` is the branch the work stacks on: the current rollup for a
rollup child, otherwise fresh `origin/test`. Make Git selectors exact.

**Reviewer of another worker's tree** (read-only, existing worktree):

```bash
orca orchestration worker-start --agent codex --model gpt-6.1-sol --effort xhigh \
  --worktree branch:<worker-branch> --task-title "🔍 REV <purpose>" \
  --spec "$(cat <brief-file>)" --json
```

`path:<worktree-path>` and `id:<repo-id>::<path>` are equivalent selectors.
Creation flags (`--name`, `--base-branch`) are rejected for existing worktrees.

**Wait, then parse the last JSON object.** `check --wait` emits NDJSON keepalive
objects (`_keepalive`, legacy `_heartbeat`) before one final pretty-printed JSON
object. Skip the keepalives and take the last object:

```bash
orca orchestration check --wait --types worker_done,escalation,question \
  --timeout-ms 900000 --json 2>&1 | python3 -c '
import json, sys
text, decoder, pos, last = sys.stdin.read(), json.JSONDecoder(), 0, None
while (pos := text.find("{", pos)) != -1:
    try:
        obj, pos = decoder.raw_decode(text, pos)
    except ValueError:
        pos += 1
        continue
    if not (obj.get("_keepalive") or obj.get("_heartbeat")):
        last = obj
print(json.dumps(last, indent=2) if last else text)'
```

Process every message in `result.messages` before acknowledging
`result.deliveryId` with the next wait (`check --ack <delivery_id> --wait ...`).
A timeout or empty result is a checkpoint, not a failure.

**Answer, follow up, inspect, settle:**

```bash
orca orchestration reply --id <message_id> --body "<answer>" --json
orca orchestration send --to dispatch:<dispatch_id> --subject "<subject>" --body "<guidance>" --json
orca orchestration worker-show --dispatch <dispatch_id> --json
orca orchestration worker-read --dispatch <dispatch_id> --source auto --limit 50 --json
orca orchestration worker-release --dispatch <dispatch_id> --json
orca orchestration worker-retain --dispatch <dispatch_id> --json
```

After each accepted `worker_done`, validate it against the expected Dispatch,
then do exactly one:

- **Follow up in the same session** where Orca accepts the handle, such as the
  terminal-backed SEC Daybreak worker: `worker-show`, then
  `worker-start --task <next_task_id> --terminal <agent_terminal_handle>`. The
  new Dispatch takes over cleanup.
- **Retain** the worker on the operator's request.
- **Release** it. `worker-read` still works after release.

Current Orca refuses the handle for agent-session workers with
`terminal_unsupported_for_agent_session` (fix pending upstream,
stablyai/orca#34043). For their follow-up, release, then start a fresh
`worker-start` whose brief carries the needed context: prior findings, files and
revision.

`send --to dispatch:<id>` is guidance for a live, unsettled Dispatch only; never
send work outside a Dispatch.

## Verify the model

The receipt's `launch.effective` is the first check. The provider's own records
confirm it; use the worker's worktree path from `worker-show`.

**Codex:** the newest `threads` row for that worktree, created after the launch:

```bash
sqlite3 -readonly ~/.codex/state_5.sqlite \
  "SELECT id, model, reasoning_effort, daybreak_enabled, rollout_path FROM threads
   WHERE cwd = '<worktree-path>' ORDER BY created_at_ms DESC LIMIT 3;"
python3 - <rollout_path> <<'EOF'
import json, sys
for line in open(sys.argv[1]):
    entry = json.loads(line)
    if entry.get("type") == "turn_context":
        p = entry["payload"]
        print(p.get("model"), p.get("effort"), p.get("cyber_access_program"))
EOF
```

**Claude:** the newest transcript in `~/.claude/projects/<slug>/`, where the
slug is the worktree path with every non-alphanumeric character replaced by
`-`:

```bash
slug=$(python3 -c 'import re, sys; print(re.sub(r"[^A-Za-z0-9]", "-", sys.argv[1]))' "<worktree-path>")
python3 - "$(ls -t ~/.claude/projects/"$slug"/*.jsonl | head -1)" <<'EOF'
import json, sys
seen = set()
for line in open(sys.argv[1]):
    entry = json.loads(line)
    if entry.get("type") == "assistant" and not entry.get("isSidechain"):
        seen.add((entry["message"].get("model"), entry.get("effort")))
print(sorted(seen, key=str))
EOF
```

When several workers share a worktree, match the record by its creation time
against the receipt. Report the verified model and effort with the result.

## Security path

Route an assignment to SEC when **any** trigger applies:

- **Trust boundary:** authentication, sessions, authorization; crypto, secrets or
  credential handling; parsing untrusted input; sandboxing and permissions;
  network-exposed endpoints; CI/release credentials and supply chain.
- **Security fix:** a vulnerability report, a Dependabot/CVE alert with reachable
  impact, or hardening.
- **Defensive-security content** standard safeguards are likely to refuse or
  degrade: exploit reproduction against your own code, malware/IOC analysis,
  fuzzing harnesses.
- **A model refused:** a Claude worker or reviewer refused on safeguards
  (`refusal`, `cyber` category), or a standard Codex model declined. Re-route that
  assignment to SEC and report it; this is a routing rule, not a fallback.
- **The operator asks.**

| Mode | When | Assignment |
| --- | --- | --- |
| **SEC-REV** | Any trigger on a change someone else implemented | In addition to REV, read-only, owning the **Security** review axis: trust boundaries, attack paths validated against reachable behavior and existing controls, severity, remediation. For a pure security fix, SEC-REV may cover all three axes and REV becomes optional. |
| **SEC-PROOF** | A security fix under `tdd` | SEC writes the failing proof, a reproduction test against the local code only. WRK (Opus 5.5) writes the fix against it, keeping proof and fix owners independent. |
| **SEC-WRK** | The implementation is itself security-domain work, or WRK refused | SEC gets WRK's write authority for the assigned files only, in its own child worktree. REV flips to Claude Opus 5.5 xhigh. If Opus refuses that review, REV runs on Codex `gpt-6.1-sol` xhigh under standard safeguards (another model and session than SEC); report that exception. |

SEC stays defensive and authorized, never exploits live systems, and no mode
relaxes "no commit, push or merge unless assigned". Never Daybreak Red.

## SEC launch

`worker-start` cannot pass Daybreak, so SEC adopts a terminal started with the
`orca-pod-sec` Codex profile (`gpt-5.6-sol`, xhigh, `daybreak = true`):

```bash
orca terminal create --worktree <sel> --title "🛡️ SEC <purpose>" \
  --command "codex --profile orca-pod-sec" --json          # returns the terminal handle
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000 --json
orca orchestration worker-start --terminal <handle> --worktree <sel> \
  --task-title "🛡️ SEC <purpose>" --spec "$(cat <sec-brief-file>)" --json
```

- `<sel>` is the coordinator's worktree for SEC-REV, or the reviewed worker's
  worktree. For SEC-PROOF and SEC-WRK, first create SEC's own child worktree
  with `orca worktree create --name <short-name> --base-branch <branch>
  --parent-worktree current --json` and select it exactly.
- Do not pass `--agent`, `--model` or `--effort` with `--terminal`. The
  receipt's `launch` fields are null for adopted terminals, so the receipt
  proves nothing about the model.
- **Verify Daybreak** from the Codex records (above): the `threads` row has
  `model = gpt-5.6-sol` and `daybreak_enabled = 1`, and the rollout
  `turn_context` has `effort: xhigh` and `cyber_access_program: daybreak_blue`.
  Report a mismatch and do not accept the result.
- **Fail closed.** If Codex refuses a turn with "Daybreak support … could not be
  confirmed", SEC reports and stops. Never use `/daybreak` to turn Daybreak off,
  and never reroute to another model.
- **Tear down** after settlement: `worker-release --dispatch <dispatch_id>`
  returns `retained` for an adopted terminal, so then run
  `orca terminal close --terminal <handle>`.

## Filter-blocked SEC

The provider's content filter can hide SEC's output: the SEC terminal shows a
notice such as "This content can't be shown" where the result belongs, and no
`worker_done` arrives. It can persist after a nudge, so act once you see it:

1. Salvage the evidence still visible with
   `orca orchestration worker-read --dispatch <dispatch_id> --source terminal --json`,
   and hand any defect it shows to the implementation owner.
2. Confirm the turn has ended before teardown: the terminal is idle at the
   Codex prompt (`orca terminal wait --terminal <handle> --for tui-idle --json`
   succeeds and the last screen shows the input prompt, not a running turn).
   Then stop the dispatch with
   `orca orchestration worker-stop --dispatch <dispatch_id> --json` and run
   `orca terminal close --terminal <handle>`. If the turn may still be running
   or its state is unverifiable, keep the terminal and dispatch, and report
   them as retained.
3. Route the targeted security re-review to REV2 (Claude Opus 5.5 xhigh) with
   the salvaged evidence, and report it as an exception.

Every SEC brief asks for findings in defect-and-fix terms: the flaw, its
location and the fix. That wording trips the filter less than attack
narratives.

## DSP dual opinion

DSP is two independent specialists on one question: Codex `gpt-6-astra` max and
Claude Opus 5.5 max.

1. Write one brief with the concrete question and evidence. Start both workers
   in the same wave, read-only, `--worktree current`, each with its own
   `--agent/--model/--effort`.
2. Keep them independent: neither sees the other's opinion.
3. Wait for both. Step ORC up to xhigh (`/effort xhigh` in Claude Code), then
   synthesize: agreements, disagreements with the evidence for each, a
   recommendation, and what would falsify it. Return to high afterward.
4. Return genuine human decisions to the operator with a recommendation.

## Review panel

A map panel or spec panel runs one fresh REV per persona on one frozen subject,
under the [panel rules](../to-spec/review-lenses/panel.md). The owning skill
names the personas and mode.

1. **Brief each persona.** Use the Brief template, with read-only authority, and
   add:

   ```text
   Panel: <map | spec> panel, round <n>.
   Persona: <persona file path>. Mode: <MAP PASS | SPEC REVIEW>.
   Lens: <the persona file's Lens line for that mode>.
   Required reads: <panel rules path>, <persona file path>, <its standard path, if any>, the subject and the governing decisions. Open your report with the reads you made.
   Subject: <repository SHA plus the inline draft | parent URL with its body, the body's lastEditedAt (or createdAt), and each child's outcome, acceptance, source links and blockers>.
   Governing decisions: <map URL with its Destination, Decisions so far and Out of scope text>.
   ```

   The brief carries the frozen subject alone: never the dialogue, the
   drafter's reasoning, another persona's output, earlier findings or the
   settled list.
2. **Start the whole wave before any waiting**, one `worker-start` per persona
   (and per A/B session), each a new session:

   ```bash
   orca orchestration worker-start --agent <opposite> --model <REV model> --effort xhigh \
     --worktree current --task-title "🔍 REV <panel> <persona> r<n>" \
     --spec "$(cat <brief-file>)" --json
   ```

   `<opposite>` is the provider opposite the record's drafter: Codex
   `gpt-6.1-sol` for a Claude drafter, Claude `claude-opus-5-5` (REV's
   alternate) for a Codex drafter. Never pass `--terminal` or resume an earlier
   reviewer.
3. **Verify every receipt** under **Verify the model**. Personas share the
   worktree, so match each provider record to its worker by creation time.
4. **Settle the wave.** A failed launch, a missing report, a missing read or a
   model or effort mismatch means not run. Recover a failed launch through
   **Commands**; retry a not-run persona once on the same assignment, only after
   the earlier attempt is settled or stopped. Never substitute a model or
   provider. Release each worker after its accepted `worker_done`.
5. **Synthesize** at ORC's xhigh alternate under the panel rules, then return to
   high.
